# WORKCHECKLIST-SITE

用户实际使用的网址：<https://tigerbearai-jpg.github.io/WORKCHECKLIST-SITE/>。

此仓库是 GitHub Pages 的前端发布代码，使用 Supabase Auth 和数据库；Google Apps Script 只属于历史迁移来源。`main` 是当前发布分支，不要未经批准将开发改动合并或推送到 `main`。

工作操作台版本已于 2026-10-28 完成生产数据库迁移并发布（代码提交 `73889ba`）。进展展示已简化为当前步骤与独立备注。本次 `feature/urgency-step-order` 增加事项紧急程度和步骤排序。

## 本次功能

- 工作操作台：全部／在途／已完成／暂停可点击切换；两处列表按所属项目、业务分类、项目状态及关键词叠加筛选。多项目事项筛选会使用所选项目本身的状态。
- 事项状态在卡片中突出显示，删除待规划和数字百分比。步骤可选；无步骤显示中性概览条，完成事项显示满条。
- 业务分类多选，保留既有多项目关联；同步适配保存、SOP 匹配、历史查询与分类重命名／合并。
- 每个工作事项可设置紧急程度：紧急、急、正常（默认）。在新增或编辑事项时选择；首页按紧急、急、正常排序，同级保持原顺序，筛选条件继续生效。
- 工作步骤提供上移／下移按钮，保存后保留新顺序；步骤ID、状态和完成日期保留，取消不会保存顺序。
- 当前进展只显示进行中的工作步骤，支持并行；不再提供独立的进展说明输入框。备注独立编辑与展示；步骤完成不自动启动下一步，并保留步骤变化日志。
- 从列表返回、取消或保存，恢复来源页、状态视图、筛选、展开步骤和滚动位置；事项退出筛选时保持附近位置。失败留在编辑页，可重试。
- GPT 工作同步下方提供工作管理要素整理：新增、改名、合并、停用、恢复、安全删除及项目状态维护。停用保留历史引用，不作为新建事项或 GPT 建议的新选项。

## 开发与验证

这是静态网页，无需打包。开发时在仓库根用 `python3 -m http.server 8000 --bind 127.0.0.1` 提供静态文件；真实登录使用现有 Supabase 配置，不更改身份认证策略。不要在聊天中粘贴密码或任何 secret/service role key。

运行测试：

```bash
npm ci
# 本云环境已有 /usr/bin/chromium；其他机器安装 Chromium 后设置 CHROMIUM_PATH。
CHROMIUM_PATH=/usr/bin/chromium npm test
```

19 项测试加载真实前端和 Supabase 适配层，通过测试查询传输运行本地 PGlite PostgreSQL。覆盖功能、数据库维护 RPC、原有多项目关联、GPT 选择器和手机布局；使用 `anon` / `authenticated` 角色验证 RLS。测试不访问真实 Supabase、不使用生产记录、邮箱或密钥。它们不代替真实部署后的登录、JWT、网络和线上权限验收。

## 审核后上线顺序

1. 审核本分支及 `database/202610270010_workbench.sql`，确认旧数据库已完成 `202610260009` 多项目迁移。相同迁移也已准备在开发资料仓库的 `supabase/migrations/` 中。
2. 备份数据库；由获授权的管理员执行新增迁移（事务内添加分类数组、备注和启用状态，保留原有列与记录，并更新维护 RPC）。未执行前不要发布新前端。
3. 验证数据库迁移完成，再经用户明确批准将本分支合并到 `main`，由 GitHub Pages 发布；核对实际部署提交及静态资源，不能只看 Git 提交成功。
4. 用授权测试账户确认登录、读写、多分类、多项目、进展、备注、返回位置、历史考核 CSV、GPT 同步，以及匿名拒读和不同用户隔离。
5. 数据库变更是加字段且保留单分类主字段；回退时保留新增数据并恢复此前前端提交，不删除列、不清空业务表。旧前端仅能展示首个分类，不能作为多分类完整验收版本。

`notes` 单独保存备注，不复用原来的信息可信度 `confidence`；历史进展保存在 `latest_progress`；新页面不再编辑或拼接该字段，保存其他内容时保留其原值。当前进展只由步骤状态生成。数据库中的 `category_names` 为完整分类数组，`category_name` 保留首个分类以兼容旧代码。不得用老前端再次编辑多分类事项，否则旧客户端可能只修改主分类。

事项紧急程度上线前，需先执行 `supabase/migrations/20261028064722_work_item_urgency.sql`。迁移仅增加work_items.urgency字段和合法值约束，已有事项默认为正常，不删除记录、不更改RLS。
